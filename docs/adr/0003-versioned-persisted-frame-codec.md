# Versioned persisted-frame codec, separate from the UART wire path

Decoded CS subevent-result frames need a versioned storage-replay contract that neither the UART wire path nor the C FFI provides, so this repo adds a dedicated persistence codec for issue #51 — `encode`/`decode` in [`mars-bluetooth-hci/src/event/hci_le_cs/persisted_frame.rs`](../../mars-bluetooth-hci/src/event/hci_le_cs/persisted_frame.rs), available via the `persisted-frame` feature (part of the default build: `std`+`alloc`+`libc`; deliberately unavailable to the embedded no-std feature set). V1 frames are byte-compatible with the FFI serializer's non-COBS postcard representation: `encode` calls the same shared core (`serialize_subevent_result_event_bytes` in `mars-bluetooth-hci/src/libc.rs`) that `serialize_subevent_result_event(&event, use_cobs=false)` uses, so a persisted frame is exactly an FFI serialization envelope whose bytes are jointly defined by the declaration order of `libc::SerializableRef` — which the owning `libc::Serializable` and the codec's private decode mirror match byte-identically — and the serde derives of `SubeventResultEvent`; any incompatible change requires a new declared version. The golden fixtures and the pinned variant tags catch every change that alters the representative frames' bytes or renumbers a payload enum's tags; appending an enum variant keeps both green while still breaking readers of the new variant, so additions are governed by review against this version policy. The public storage contract is deliberately narrower than the general FFI `Serializable` enum: decode uses a private, unboxed, byte-identical wire mirror. Versioning is out-of-band through a `FrameDescriptor` (format name `mars-hci-cs-subevent`, current version 1) — `encode` emits bare frame bytes with no in-band version, the caller stores the descriptor returned by `current_frame_descriptor()` alongside the bytes (e.g. in the storage record or file name), and `decode` dispatches only on the declared descriptor, never guessing from the bytes; this decides nothing about in-band versioning for the UART wire path, which remains open as #15. Both directions validate the event's counts (`SubeventResultEvent::validate_invariants`), so every frame the codec writes replays through `decode`. Decode is strict — the whole input must be one frame: padded, over-written, or concatenated records are rejected with `TrailingBytes`, a truncated record fails decode inside postcard (`Decode`), a leading byte that is not a V1 envelope tag is rejected with `UnknownEnvelopeTag` (written by a different envelope schema or corrupted — not a truncated or padded record of this one), a well-formed log-message envelope is rejected with `UnexpectedFrameKind` (a log record with corrupt bytes fails decode inside postcard), and an event breaking the parser's step or antenna-path bounds is rejected with `InvalidEvent` — the codec validates these count bounds, not the deeper semantic consistency of the stored event, which decodes as stored exactly as the FFI serializer would have encoded it. And `decode` accepts exactly the versions with an explicit dispatch arm, normally only the current version; during a release migration the immediately preceding version's decoder arm and fixture directory are retained, and both are removed in the same change once the migration completes. Compatibility is pinned by committed golden fixtures — `mars-bluetooth-hci/tests/fixtures/persisted-frames/vN/modeN.postcard.hex` plus `config-complete.postcard.hex` per retained version (the config-complete frame pins the initial-metadata half of the format, which carries no steps and hence has no mode file): current-version fixtures are locked byte-for-byte to the current encoder, while a retained migration-source version's fixtures are decode-verified through their declared descriptor (they exist precisely because the current encoder no longer produces their bytes). The known V1 cost is accepted deliberately: the event's fixed `[Step; 160]` array serializes in full, so every frame is ~13.3 KB regardless of `step_count` (the in-memory event is ~16 KB, `Step` × 160 plus header fields); that is the price of byte-compatibility, and compacting frames requires a new declared version. See [`docs/wire-format.md`](../wire-format.md) §Versioning and compatibility and [`docs/architecture.md`](../architecture.md) §Persisted-frame replay for the contract consequences.

## Considered Options

- **In-band version byte in every persisted frame.** Rejected for V1: byte-compatibility with the existing FFI non-COBS representation is the point of the contract; the wire-path question remains open as #15.
- **The general FFI `Serializable` enum as the public storage contract.** Rejected: the storage contract must be independently versioned and must not drag the FFI surface along with every change.
- **Decoding through the public boxed `Serializable`.** Rejected: it pays an ~16 KB heap allocation plus a copy of the event per replayed frame; the private unboxed wire mirror is byte-identical and avoids both.
- **Compact variable-length step serialization.** Rejected for V1: it breaks byte-compatibility; the fixed-array cost (~13.3 KB per frame regardless of `step_count`) is documented instead, and compaction requires a new declared version.
